# ADR 0001: Repository declarations are evidence-derived, not config-authored

- **Status:** Accepted
- **Date:** 2026-06-15

## Context

The repository publishes machine- and human-readable declarations (`FAIR.md`,
`TRUST.md`, `AI-declaration.md`, the design declaration, `CITATION.cff`,
`codemeta.json`) generated by `scripts/generate-declarations.py`. The early
FAIR/TRUST renderers embedded repository-specific prose (e.g. naming RO-Crate
and MCP) directly in Python. That phrasing would be wrong in any other
repository the generator is reused in.

The obvious fix — move the narrative into `.declarations.yml` so each repo can
author its own prose — was considered and rejected. Free-text prose in config is
never checked against reality, so it drifts: the day the underlying code is
removed but the sentence is not, the declaration asserts something false. A
declaration that can lie is worse than none, and the whole reason to *generate*
declarations is that they cannot. Config prose also forces every new repo to
author text and duplicates the standard's framework wording everywhere.

## Decision

Declarations are **derived from verifiable repository evidence**, not authored as
free text. We separate three layers:

1. **Framework text** (the FAIR/TRUST principle definitions) is owned centrally
   in the generator and pinned by `vocabulary_version`. It is identical across
   all repos and changes only when the external standard does.
2. **Capabilities** — `{id, label, rationale, signals}` — name the specifics
   (RO-Crate, MCP, …). A capability is claimed **only** when at least one of its
   `signals` exists in the repo. The label/rationale are owned centrally so they
   read identically everywhere.
3. **Configuration** (`.declarations.yml`) holds what cannot be detected
   (people, identifiers, policy stances) and **per-repo extensions** of the
   generic core: extra trigger `signals` and extra `capabilities`. Crucially,
   config-supplied capabilities and signals are still **evidence-gated** — they
   only ever surface when their paths exist — so configuration can point the
   tool at this repo's files but can never fabricate a claim. Optional
   `capability_notes` annotate already-detected capabilities.

The generic core lives in the generator (repo-agnostic, version-pinned); repo
specifics live in config. This keeps the generator portable and ready to extract
into a shared tool without rewriting it.

The invariant is: **no evidence, no claim.**

## Consequences

- Declarations are truthful by construction; a repo that drops a capability
  stops claiming it automatically, with no human in the loop.
- The universal parts (standard wording, capability labels) live once and
  propagate to every repo on a `vocabulary_version` bump.
- New repositories describe themselves accurately with zero prose authoring,
  which is what makes the generator portable across many repos.
- Recognizing new technology is additive: add one `Capability` entry, not edits
  to N renderers or N config files.
- Editorial phrasing that is genuinely per-repo is limited to opt-in
  `capability_notes` attached to already-detected capabilities.
